- [x] **M0-01 · Branch and tag**
  - Tag the v1 hand-in commit `v1.0.0` on `main`. Create branch `feat/v2-dev` from it. All v2
    work lands there, one commit per work package ([10 §4](../10-quality.md)).
  - Done when: tag and branch exist, `docs/v2/README.md` status says *in progress*.

- [x] **M0-02 · Move the outbox into service-kit**
  - Move `services/routine-service/src/outbox.ts` to `libs/service-kit/src/outbox.ts`
    (`enqueue`, `OutboxRelay`, `purgePublished`) and export it. Add
    `libs/service-kit/migrations/outbox.sql` (the v1 `outbox` table DDL) and
    `runKitMigrations(pool, ['outbox'], logger)` that applies kit migrations idempotently
    (tracked in the same `schema_migrations` table as service migrations, names prefixed
    `kit:`).
  - routine-service imports from the kit. Its `001_init.sql` already has the table, so
    `runKitMigrations` must detect the existing table and record `kit:outbox` without running
    it.
  - Done when: behaviour unchanged, `npm test` green, `scripts/demo.sh all` green.

- [x] **M0-03 · Manifest types**
  - `libs/service-kit/src/manifest.ts`: the types of [04 §2](../04-domain-platform.md),
    `validateManifest` (ajv against the schema), `manifestDigest` (SHA-256 of canonical
    JSON, keys sorted recursively).
  - `contracts/schemas/domain-manifest.v1.schema.json` generated by hand from the types.
  - Tests: valid/invalid manifests, digest stable under key reordering.

- [x] **M0-04 · Widen capability type pattern and add `context`**
  - `contracts/schemas/action-requested.v1.schema.json`: `actionType` pattern
    `^[a-z][a-z0-9]*\.[a-z][a-zA-Z0-9]*$`, optional `context` object ([05 §3](../05-messaging.md)).
  - `action-failed.v1.schema.json`: `error.code` enum = codes of [05 §6](../05-messaging.md) (plus
    legacy values `PermanentError`, `TransientError`, `Error`, `SubRoutineFailed` accepted for
    compatibility).
  - `execution-failed.v1.schema.json`: optional `errorCode`, `failedActionType`.
  - Update `contracts/asyncapi/routine-messaging.yaml`.
  - Done when: existing contract tests pass, new tests for widened pattern.

- [x] **M0-05 · Error codes in workers**
  - Add `code` to service-kit `PermanentError`/`TransientError` (constructor option, default
    `INTERNAL`). Workers set codes: integration-worker maps HTTP status as in [05 §6](../05-messaging.md),
    SSRF → `FORBIDDEN_HOST`, timeouts → `TIMEOUT`, network → `UNREACHABLE`. task-service and
    notification-service param errors → `INVALID_PARAMS`, missing list → `REFERENCE_GONE`
    (v1 falls back to the default list: keep that behaviour, no error). Engine template errors
    → `TEMPLATE_ERROR`, sub-routine → `SUBROUTINE_FAILED`.
  - routine-service stores `execution_actions.error_code` (migration `008_error_codes.sql`,
    column only) and puts `errorCode` into `ExecutionFailed`.
  - Tests: status → code table; engine stores the code.

- [x] **M0-06 · Roles**
  - Keycloak (the v1 identity provider, see [identity-service.md §6](../services/identity-service.md)):
    realm role `admin`, demo user admin, `roles` claim in tokens. (Planned as `users.role` and
    `ADMIN_EMAILS` in a custom identity-service.)
  - service-kit `AuthUser` gains `roles`; add `requireAdmin(request)`.
  - gateway: `/api/v1/system/**` except `status` requires admin (status stays open to users:
    the v1 Infrastructure page must keep working for non-admins, read-only).
  - Tests: non-admin `403` on an admin route.

- [ ] **M0-07 · Service accounts and internal auth**
  - identity-service: `service_accounts`, `POST /api/v1/auth/service-token`, seeding from
    `SERVICE_ACCOUNTS`.
  - service-kit `internal-auth.ts`: `installServiceAuth(app, allowed: string[])` for
    `/internal/` (checks `aud: routine-internal`, `sub: service:<name>` ∈ allowed) and
    `serviceTokenProvider(name, secret)` (fetches and caches a token, refreshes at 80 % of its
    lifetime).
  - compose + `deploy/stack.yml`: `SERVICE_ACCOUNTS` and per-service `SERVICE_TOKEN_SECRET`.
  - Tests: user token rejected on `/internal`, service token accepted, unknown service rejected.

- [ ] **M0-08 · New exchanges**
  - `infra/rabbitmq/definitions.json`: exchanges `domain.events`, `today.cards`,
    `platform.registry`, `routine.commands` (topic, durable). No queues yet.
  - Done when: `docker compose up` loads them, and the Infrastructure topology still renders.

- [ ] **M0-09 · CI and compose scaffolding for new services**
  - `docker/node-service.Dockerfile` unchanged. Add a `domains-db` Postgres to compose with an
    init script `infra/postgres/domains-init.sql` that creates one database + role per new
    service (budget, health, people, home, calendar, trigger, today, delivery, connector,
    assistant). Compose profiles as in [03 §7](../03-architecture.md).
  - A template workflow `.github/workflows/_template-new-service.md` (instructions, not a
    workflow) describing how to add `<service>.yml` for a new service.
  - Done when: `docker compose --profile all config` validates.
